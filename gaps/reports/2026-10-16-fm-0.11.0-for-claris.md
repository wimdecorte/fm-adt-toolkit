# fm CLI 0.11.0 (29863806): findings for Claris

Six findings from the intake of fm CLI 0.11.0. Each section below is one ticket: the heading is
the summary, and the fields under it map onto Jira's. Every reproduction starts from a new file made
with `filemaker --create`, so none needs anyone else's data. A step written "in FileMaker Pro" means
written through Script Workspace's own step dialog.

**Environment, all findings:** fm CLI 0.11.0 (build 29863806), installed at
`~/.local/bin/filemaker`; FileMaker Pro 26.1.1 (build 033); macOS 26 (Darwin 25.6). Files opened
by path, or over `fmnet://localhost/<name>` when FileMaker Pro shares them.

| # | Summary | Type | Suggested priority |
|---|---|---|---|
| 1 | Truncate Table's `table` is a table occurrence; FileMaker stores a base table | Bug | High |
| 2 | `read:script` `problems` flags fieldless Set Field and Cut, which FileMaker does not | Bug | Medium |
| 3 | Configure Region Monitor Script's script parameter has no key | Bug | Medium |
| 4 | Import Records' calculated XML and XSL paths have no key | Bug | Medium |
| 5 | A field reference stored with id 0 reads exactly like no field reference | Bug | Low |
| 6 | Whether a block is collapsed cannot be read | Improvement | Low |

## 1. Truncate Table: `table` is resolved as a table occurrence, but FileMaker stores a base table

- **Type:** Bug
- **Suggested priority:** High. The reference fails silently in both directions. A step fm writes
  shows `<Table Missing>` in FileMaker Pro while fm reads it back as valid. A step FileMaker Pro
  wrote loses its table on every read, so a read-modify-write through fm cannot keep it.
- **Component:** fm CLI › script steps › Truncate Table (step 182); `read:script`, `create:script`
- **Affects version:** 0.11.0 (29863806). Through 0.10.0 the stored id was readable as the unnamed
  `slots.memberKey`.

**Description.** `filemaker help script steps "Truncate Table"` documents `table` as type
`tableOccurrence`. FileMaker stores the step's table as a base table reference: Save as XML writes it
as `ParameterValues/Parameter/List/BaseTableReference`. The two never meet. A base table id read as an
occurrence id finds nothing, and the occurrence fm writes is not a base table FileMaker can find.

**Steps to reproduce (write direction).**
1. `filemaker --file=/tmp/tt.fmp12 --create /dev/null` — the new file has one table, `tt`, and its
   occurrence `tt`.
2. Write this op, then read the script back in a new process:
   ```json
   {"op":"create:script","name":"t-truncate-1","body":[{"stepID":182,"tableSelection":1,"table":"tt","withDialog":false}]}
   {"op":"read:script","name":"t-truncate-1"}
   ```
3. Open `/tmp/tt.fmp12` in FileMaker Pro and look at the step in Script Workspace.

**Expected result.** Script Workspace shows `Truncate Table [ With dialog: Off ; Table: “tt” ]`.

**Actual result.** The create succeeds, with the warning `step 'Truncate Table' (/0) has a problem
in its options`. The read returns `"table": "tt", "tableSelection": 1`. Script Workspace shows
`Truncate Table [ With dialog: Off ; Table: <Table Missing> ]`, marked as a problem step.

**Steps to reproduce (read direction).**
1. In the same file, in FileMaker Pro, add Truncate Table with Specify table → `tt`. Script
   Workspace shows `Table: “tt”`.
2. `read:script` that script with fm.

**Expected result.** `"table": "tt"`, as documented.

**Actual result.** `"tableSelection": 1, "withDialog": false`, and no `table`. Observed on two
steps written this way in an existing file, where Script Workspace prints `Table: “<name>”`; the
read direction has not been re-run on a new file. Their stored ids (131 and 139) are base table ids,
and neither is an occurrence id in that file. 0.10.0 returned the same ids as `slots.memberKey`.

**Notes.**
- `tableSelection` means 1 = specified table and 0 = current table, by Script Workspace's text.
- With `tableSelection: 0` plus a `table`, FileMaker shows `<Current Table>`, yet fm reads the
  ignored `table` back as though it were in effect.
- That fm stores an occurrence id on write is inferred from the documented key type and the two
  symptoms. A Save as XML export of `/tmp/tt.fmp12` after step 2 shows the stored id directly.

## 2. `read:script` `problems` lists fieldless Set Field and Cut steps that FileMaker does not flag

- **Type:** Bug
- **Suggested priority:** Medium. `problems` is documented as FileMaker's own problem-step check,
  and a consumer relying on it reports intact steps as broken.
- **Component:** fm CLI › `read:script` › `problems`
- **Affects version:** 0.11.0 (29863806)

**Description.** fm's help says `problems` is "the same live re-check that puts FileMaker Pro's red
'problem step' flag on a step in the Script Workspace". For a Set Field or Cut written with no
target field (both act on the active field, which is valid and saves without complaint), `problems`
lists the step, while FileMaker Pro does not mark it.

**Steps to reproduce.**
1. `filemaker --file=/tmp/pr.fmp12 --create /dev/null`
2. Write, then read in a new process:
   ```json
   {"op":"create:field","table":"pr","name":"F","type":"text"}
   {"op":"create:script","name":"fieldless","body":[{"stepID":76,"field":"pr::F","value":"1"},{"stepID":76,"value":"1"},{"stepID":46,"field":"pr::F"},{"stepID":46}]}
   {"op":"read:script","name":"fieldless"}
   ```
   Run the `create:field` in a batch of its own before the `create:script`.
3. Open the file in FileMaker Pro and look at the script.

**Expected result.** `"problems": []`. All four steps are intact, and Script Workspace marks none of
them.

**Actual result.** `"problems": [{"path":"/1","step":"Set Field"},{"path":"/3","step":"Cut"}]`.
Script Workspace shows `Set Field [ 1 ]` and `Cut [ Select ]`, neither marked as a problem step.

**Notes.** Once the field is deleted, `problems` lists all four steps, and FileMaker marks the two
that named it (`Set Field [ pr::<Field Missing> ; 1 ]`, `Cut [ Select ; pr::<Field Missing> ]`). That
part agrees. Only the two fieldless steps disagree.

## 3. Configure Region Monitor Script: the script parameter has no key

- **Type:** Bug
- **Suggested priority:** Medium. The value is lost on every read, and it cannot be authored.
- **Component:** fm CLI › script steps › Configure Region Monitor Script (step 185)
- **Affects version:** 0.11.0 (29863806). 0.10.0 returned it as the unnamed `slots.calc.0`.

**Description.** Script Workspace prints the step's script parameter (`… ; Script: “s” ; Parameter:
1 ; …`). `filemaker help script steps "Configure Region Monitor Script"` documents no key for it.
0.11.0 sends the value under no key, and a write naming one is refused.

**Steps to reproduce.**
1. In FileMaker Pro, in any file, add Configure Region Monitor Script: Monitor iBeacon, any script,
   Parameter `1`. Script Workspace shows `Parameter: 1`.
2. `read:script` that script with fm.
3. Write the same step with fm:
   ```json
   {"op":"create:script","name":"t-region","body":[{"stepID":185,"monitor":"iBeacon","name":"\"n\"","beaconUuid":"$U","scriptReference":"<any script>","parameter":"1"}]}
   ```

**Expected result.** The read carries the parameter under a documented key, and the write accepts
the same key.

**Actual result.** The read returns `monitor`, `name`, `beaconUuid` and `scriptReference`, and no
parameter. Observed on five such steps in an existing file; not re-run on a new one. The write is refused: `unknown_step_option`, "'Configure Region Monitor Script' has no
option 'parameter'".

## 4. Import Records: a calculated XML source or XSL path has no key

- **Type:** Bug
- **Suggested priority:** Medium. The source of an XML import is lost on read whenever it is given
  by calculation.
- **Component:** fm CLI › script steps › Import Records (step 35); `importOptions`
- **Affects version:** 0.11.0 (29863806). 0.10.0 returned the calculations as the unnamed
  `slots.calc.0` (XML) and `slots.calc.1` (XSL).

**Description.** For an XML data source, Script Workspace prints the source and the XSL file, for
example `Import Records [ With dialog: Off ; $PathXML; http://example.com/x.xsl ]`. A literal URL or
path travels inside `importOptions.profile.dataRaw`, which fm carries undecoded (XOR 0x5A). A path
given by calculation does not, and no documented key carries it.

**Steps to reproduce.**
1. In FileMaker Pro, add Import Records with an XML data source: XML from a calculated value, `$x`;
   XSL from a calculated value, `$y`.
2. `read:script` that script with fm, and decode `importOptions.profile.dataRaw` (XOR each byte with
   0x5A).

**Expected result.** `$x` and `$y` are present under named keys.

**Actual result.** Neither appears in the step, nor in the decoded `dataRaw`. Literal paths entered
the same way do appear, decoded: `…XMhttp://example.com/x.xml…` for the XML source,
`…[^fileZ]x.xsl` for a file XSL. Observed on seven XML imports in an existing file; not re-run on a
new one.

## 5. A field reference stored with id 0 reads exactly like a step with no field reference

- **Type:** Bug
- **Suggested priority:** Low. A broken reference is reported as no reference at all.
- **Component:** fm CLI › `read:script` › field-reference keys (Set Field, Cut, Copy, Clear, Paste,
  Go to Field, Insert Text and others)
- **Affects version:** 0.11.0 (29863806). Through 0.10.0, bit 0x1 of the step's `flags` was set on
  such a step and clear on a fieldless one, so the two could be told apart.

**Description.** A deleted field or table is reported by the ids still stored, as `field:
{"occurrence":"t","fieldId":1}`, which is useful and consistent. A reference stored with id 0 and
no table occurrence is a different case: Save as XML writes it as `<FieldReference id="0" name=""
UUID="">`, and Script Workspace prints `<Table Missing>`. 0.11.0 sends no `field` for such a step,
exactly as for a step written with no field. `problems` does not separate the two either (see
finding 2).

**Steps to reproduce.** How FileMaker comes to store id 0 is not known: the 18 observed steps came
from a file of unknown history. To observe one, export a file holding such a step with Save as XML,
find a `FieldReference id="0"`, and `read:script` its script.

**Expected result.** Some key on the step says a field reference is stored, for example `field:
{"fieldId":0}`, the same id shape already used for a deleted field.

**Actual result.** No key distinguishes the step from one with no field.

## 6. Whether a script block is collapsed cannot be read

- **Type:** Improvement
- **Suggested priority:** Low. Script Workspace does not print it, so it costs no step text. It is
  state a read returned through 0.10.0 and no longer returns.
- **Component:** fm CLI › `read:script` › If, Else If, Else, Loop, Open Transaction
- **Affects version:** 0.11.0 (29863806). 0.10.0 returned `collapsed: true|false`.

**Description.** fm's help says options a step has no key for, "for example whether a block is
collapsed in Script Workspace, are kept from the existing step when the body claims it by `uuid`".
Measured, and confirmed: a block collapsed in FileMaker Pro stays collapsed after an `update:script`
that edits another step. A read, though, cannot tell a collapsed block from an expanded one.

**Steps to reproduce.**
1. In FileMaker Pro, add `If [ ] … End If` with one step inside, and collapse the If.
2. `read:script` with fm.

**Expected result.** A read-only key on the opener, such as `collapsed: true`.

**Actual result.** `{"stepID":68,"step":"If","block":{"role":"opener","start":0,"end":2}}`, with
nothing about the collapsed state.
